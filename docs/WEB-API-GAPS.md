# Чего фронту не хватает в API

Составлено при пересборке `apps/web` на дизайн-системе (ветка `feat/web-redesign`).
Сверено построчно с 27 обработчиками в `apps/api/src/**/*.controller.ts`
(глобальный префикс `/api`) и с `apps/api/prisma/schema.prisma`.

`apps/api` в этой работе не менялся. Документ — постановка задачи на бэкенд,
а не список обходных путей. Ни одна из перечисленных дыр на клиенте не
замокана: там, где поля нет, экран показывает блок неактивным и пишет причину.

---

## 1. Отсутствующие поля

Прототип «NomadCore Владелец 360» печатает на карточке брони четыре
значения, которых в схеме нет ни у `Booking`, ни у `Guest`:

| Что показывает прототип | Состояние |
|---|---|
| Код брони («B-1044») | поля нет; `id` — это `cuid()`, владельцу его не назовёшь |
| Гражданство гостя | поля нет |
| Число гостей (`pax`) | поля нет; `RoomType.capacity` — это вместимость номера, а не факт заселения |
| «Паспорт предъявлен» / «Не предъявлены» | поля нет |

Последнее — не косметика. На нём висит целый сценарий: при заселении без
документов прототип показывает шторку «Заселить без документов?» с
пояснением «паспортные данные можно внести позже, до конца суток». Без поля
сценарий не существует.

Предлагаемый минимум: `Booking.code` (или человекочитаемый публичный
идентификатор), `Booking.pax Int`, `Guest.citizenship String?`,
`Guest.documentNo String?`. Последнее уже описано в
`nuxt/API-CONFLICTS.md` как поле с разрешением конфликтов по last-write.

## 2. Отсутствующие эндпоинты

### `GET /api/bookings/:id` — нет

Одиночную бронь загрузить нечем. «Занятость» отдаёт только `bookingId`,
и карточка вынуждена искать бронь в уже загруженном диапазоне
(`useBookings().byId`). Бронь за пределами горизонта в 21 день не откроется
вовсе — экран честно пишет «Бронь не найдена среди загруженных».

### `PATCH /api/bookings/:id` — нет

После создания неизменяемы: даты, номер, гость, заметки, цена. Сервер умеет
ровно один переход — `PATCH /api/bookings/:id/status` с телом `{ status }`.

Из-за этого не реализуемы три действия карточки: **«Продлить на 1 ночь»**,
**«Ранний выезд сегодня»** и **«Отметить документы»**. В интерфейсе они
оставлены на своих местах неактивными, с подписью причины.

### `DELETE /api/bookings/:id` — нет

Отмена только через переход статуса в `CANCELLED`. Для интерфейса это
приемлемо, но отменённые брони остаются обычными строками в `bookings`
и в индексе `[roomId, checkIn, checkOut]` — любой запрос занятости обязан
отфильтровывать их вручную.

## 3. Поведение, которое ломает экраны

### `GET /api/bookings` молча теряет сегодняшние выезды

Условие в `bookings.service.ts`: `checkIn < to && checkOut > from`.
Запрос `from=сегодня&to=завтра` даёт `checkOut > сегодня` и **исключает все
брони с `checkOut = сегодня`** — то есть ровно те выезды, ради которых
существует экран «Сегодня».

Обход на клиенте: окно всегда расширяется на сутки назад, отбор идёт
локально (`useBookings.ts`). Работает, но это обход, а не решение:
владелец с большим объектом получает лишние данные на каждый запрос.

Сюда же: `from` и `to` работают только парой. Передать один — значит молча
получить всю историю. Пагинации нет нигде.

### Конфликт версий приходит как `500`, а не `409`

`ChangeStatusDto` содержит одно поле `status`. Ни `expectedVersion`,
ни заголовка `If-Match`. Сервер сам читает бронь и пишет
`update where { id, version }`; при промахе Prisma бросает `P2025`,
который никто не ловит.

Следствие: клиент **не может отличить конфликт версий от поломки сервера**.
`Booking.version` в схеме есть и в ответах приходит, но принять его обратно
API не умеет — оптимистичный лок односторонний.

### `409` сегодня означает бизнес-отказ, а не конфликт версий

Это инверсия того, что предполагает `nuxt/API-CONFLICTS.md`:

| Код | Что предполагал дизайн | Что отдаёт API сейчас |
|---|---|---|
| `409` | конфликт версий, решает владелец | `{code:"OVERBOOKING"}`, `{code:"INVALID_TRANSITION"}` — решать нечего |
| `422` / `423` | бизнес-отказ | не возвращается никогда |
| конфликт версий | `409` с телом | `500` |

Раскладка кодов в очереди мутаций сделана по РЕАЛЬНОМУ контракту:
`409` с полем `code` → `rejected`, `409` с телом `booking` → `conflict`
(задел на будущее, сегодня не срабатывает), `422`/`423` → `rejected`.

### Нет идемпотентности

Ни `POST /api/bookings`, ни `PATCH .../status` не принимают ключ
идемпотентности. Повторная отправка мутации из офлайн-очереди после
оборвавшейся сети создаёт дубль брони — либо ловит `OVERBOOKING`
на собственную же первую попытку.

### `GET /api/availability` разрежён

Свободных дней в ответе нет вовсе — только занятые ячейки. Ни `checkIn`,
ни `checkOut` в ячейке нет, поэтому многодневную полосу пришлось бы
собирать группировкой по `bookingId`. Валидации `from`/`to` нет
(ни DTO, ни pipe), ограничения диапазона тоже (92 дня стоят только
на публичном `/api/public/:slug/availability`).

Поэтому «Занятость» считается из списка броней, а не из этого эндпоинта.
Побочная выгода: список броней знает про локальные неотправленные
изменения, а `/availability` — нет.

### Нет канала «что изменилось»

`GET /api/bookings` фильтрует только по пересечению дат: ни `updatedSince`,
ни курсора, ни `Last-Modified`. Outbox (`OutboxEvent`) внутренний,
контроллером не выставлен. Единственная стратегия сверки — полная
перезагрузка, причём без пагинации.

## 4. Мелочи, замеченные при сверке

- Разнобой в кодах ошибок: rooms/room-types/guests/availability отдают
  **403 `NO_PROPERTY`**, а bookings и billing — **404 `PROPERTY_NOT_FOUND`**.
- `PATCH /api/bookings/:id/status` при чужой брони отдаёт голый
  `403 Forbidden` без машиночитаемого кода — единственный такой ответ в API.
- Ответ `PATCH .../status` не включает `room.roomType`, хотя `GET /bookings`
  включает: после перехода карточка теряет название типа номера.
- `POST /api/bookings` с `guestId` из чужого объекта попадает в
  `findFirstOrThrow` → **500**, а не 404.
- `POST /api/public/:slug/bookings` пишет `source: "marketplace"` — третье
  значение, которого нет в `@IsIn(["manual","bot"])` у `CreateBookingDto`.
- `Booking.priceTotal` и `RoomType.basePrice` — `Decimal(10,2)`, приходят
  СТРОКОЙ. Сравнивать их как числа нельзя (см. `utils/money.ts`).
- У `Room`, `Guest`, `RoomType` колонки `version` нет вовсе: их правки —
  безусловный last-write.
