# Контракт разрешения конфликтов — требование к API

Статус: **решение принято — выбор за владельцем. На бэкенде не реализовано,
требует отдельной задачи.**
Заведено на Этапе 2 по итогам проектирования офлайн-слоя.

Короткая формулировка решения: **last-write отменяется для `checkIn`,
`checkOut`, `status` и `roomId`; для остальных полей сохраняется.** По
четырём перечисленным полям сервер обязан вернуть обе версии и ждать выбора
человека.

## В чём расхождение

Исходное описание системы: «конфликты решаются last-write плюс колонка
`version` как оптимистичный лок».

Интерфейс, спроектированный на Этапе 2, этого контракта **не выполняет**.
Экран «Очередь» при конфликте показывает владельцу оба значения — своё и
серверное, — кто и когда изменил запись, и две равнозначные кнопки:
«Оставить моё» / «Принять серверное». Автоматической записи последнего
пишущего для дат и статуса нет.

Это осознанное изменение, а не недосмотр вёрстки, и его нельзя закрыть
на клиенте: клиент не может показать серверное значение, если сервер его
не прислал.

## Почему дизайн отказался от last-write

Владелец офлайн продлевает гостя до 11 августа. Одновременно администратор
с другого устройства оформляет ранний выезд 8-го. Сеть возвращается.

При last-write выигрывает тот, чей запрос пришёл вторым. Если это ранний
выезд — номер освобождается и уходит следующей брони, **а гость физически
живёт в комнате**. Владелец узнаёт об этом, когда на пороге стоят двое.

Цена ошибки здесь не «перезаписанное поле», а выселенный человек и
испорченная репутация дома в посёлке, где все друг друга знают. Автоматика
не имеет данных, чтобы выбрать правильно: оба изменения корректны, знает
только человек.

## Разделение полей

| Поле | Разрешение | Обоснование |
|---|---|---|
| `checkIn`, `checkOut` | **владелец** | двойное заселение, выселение живого гостя |
| `status` | **владелец** | отмена подтверждённой брони, заселение отменённой |
| `roomId` | **владелец** | овербукинг |
| `guest.documentNo` | last-write | монотонно: документы появляются, не исчезают |
| `guest.fullName`, заметки | last-write | цена ошибки — опечатка |
| `pax`, `rate` | last-write | правится на месте, конфликтует редко |

Формально: last-write допустим там, где обе версии совместимы. Даты, статус
и номер задают физическое размещение людей — там совместимости нет.

## Что должен делать API

**1. Отвечать 409 с телом, а не пустым статусом.**

`PATCH /api/bookings/:id` с заголовком `If-Match: <version>`. При устаревшей
версии — `409 Conflict`:

```json
{
  "booking":    { "...": "полное текущее состояние на сервере" },
  "changedBy":  "Нурбек · устройство «Ресепшн»",
  "changedAt":  "2026-08-07T12:48:00+06:00",
  "changedFields": ["checkOut"]
}
```

Без `booking` в теле клиенту нечего показать в колонке «На сервере», а без
`changedBy` / `changedAt` владелец не понимает, чьё это изменение и не
устарело ли оно само.

**2. Принимать повторную отправку на новой версии.**

Выбор «Оставить моё» отправляет ту же мутацию с `If-Match`, равным версии из
409-ответа. Сервер обязан её принять, если за это время не появилась третья
версия. Отдельного «force»-флага не нужно — и не нужно его добавлять: он
превратится в тот же last-write через чёрный ход.

**3. Различать 409 и 422.**

`409` — конфликт версий, решает владелец. `422`/`423` — бизнес-отказ
(номер занят другой бронью), решать нечего: интерфейс предлагает переселить
или отклонить. Сейчас клиент различает их по коду, и объединять их нельзя.

**4. Не терять `changedBy` в аудите.**

Поле берётся из журнала изменений брони. Если журнала нет — он тоже часть
этой задачи: без имени и времени экран конфликта показывает два безымянных
значения, и владелец выбирает наугад.

## Что происходит с очередью, пока владелец не выбрал

Мутация остаётся в очереди со статусом `conflict`. Правила:

1. **Бронь блокируется, остальные — нет.** Очередь упорядочена по времени, и
   мутации по одной броне отправляются строго последовательно. Конфликтная
   мутация блокирует только свою бронь; изменения по другим броням продолжают
   уходить. Иначе один спорный гость останавливает весь дом.

2. **Локальное состояние не откатывается.** Экран показывает значение,
   которое ввёл владелец, с пометкой «Не отправлено». Молчаливый откат к
   серверному был бы тем же last-write, только незаметным.

3. **Бронь помечена во всех списках.** Красная плашка «Конфликт версии» стоит
   в строке списка и в карточке, а не только на экране очереди.

4. **Новые изменения той же брони разрешены** и встают в очередь за
   конфликтной. После разрешения они отправляются в исходном порядке —
   на версии, полученной в результате выбора.

## Если владелец не выберет никогда

Это штатный исход, а не сбой: конфликт мог возникнуть по брони, которая уже
не важна. Правила:

- **Ничего не отправляется само.** Ни по таймауту, ни при переустановке
  приложения, ни при выходе из аккаунта. Отложенная автоотправка — тот же
  last-write, только через месяц и без свидетелей.
- **Конфликт не истекает и не удаляется.** Счётчик на вкладке «Очередь»
  остаётся красным, пока решение не принято.
- **Сервер живёт своей жизнью.** Серверная версия остаётся действующей: для
  всех остальных устройств бронь уже разрешена. Нерешённый конфликт — это
  только неотправленное изменение на одном телефоне.
- **Снимок сервера устаревает.** Если запись изменили ещё раз, при повторной
  отправке «Оставить моё» снова вернётся `409` — уже с новым снимком, и
  владелец выберет заново. Число повторов не ограничивается.
- **Очистить очередь можно только явно** — действием «Отклонить» в карточке
  конфликта. Оно удаляет мутацию и снимает пометку с брони.

## Что уже готово на клиенте

`nuxt/composables/useSync.ts` — состояния `conflict` и `rejected` в очереди,
`keepMine()` и `takeServer()`, снимок сервера в `QueuedMutation.server`.
`nuxt/components/ConflictCard.vue` — экран выбора.

Пока API не отдаёт тело 409, клиент показывает конфликт без колонки
«На сервере»: выбор превращается в «повторить или отменить». Это деградация,
а не рабочий сценарий.

## Оценка

Со стороны бэкенда: тело 409, журнал изменений с автором, разделение
409/422. Оценивается отдельно от интерфейса и в бюджет Этапа 2 не входит.
